# 从个人资料库到独立研究：我的 AI 研究工作流

这套工作流由两个 Skill 组成：kk-knowledge-base 负责个人知识库，kk-research 负责独立研究。本文记录我为什么这样设计，以及它们如何配合使用。

## 我希望解决什么问题

做研究时，我会持续积累文章、报告和会议资料。我希望这些资料能够方便地保存、查找和阅读，也希望在提出一个研究问题时，AI 能找到相关原文，带着清楚的来源和限制与我讨论。

除了资料本身，我还关心模型在回答之前究竟读到了什么。日常对话中有历史聊天、工具说明、报错和重试记录，也可能有其他模型的分析。如果这些内容都进入研究模型的上下文，我就很难判断它的结论受到了哪些影响。

因此，我把工作流分成两部分：个人知识库负责保存和提供材料，独立研究模式负责分析和讨论。具体实现之前，需要先说明我对 Agent 基座和知识库路径的选择。

## 一、围绕投研任务选择 Agent 基座

### Model Harness 影响模型怎样工作

选择 Agent 基座时，我会同时考虑模型能力和配套的运行框架。这个框架通常称为 Model Harness，负责组织上下文、调用工具、管理权限和任务状态，以及处理重试和结果验证。同一个模型放进不同的框架，执行表现和使用体验也可能不同。

一体化 Agent 产品通常已经把这些环节整合起来。对轻量投研辅助任务，我倾向于先使用一体化产品，再通过 API 或 MCP 接入第三方数据，以减少部署和交互负担。

当任务发展为深度研究等长程工作流时，我更看重执行过程能否按自己的研究方法调整。因此，我希望用开源架构 Agent 承担需要深度定制的投研生产任务，并把经过验证的方法沉淀为可复用的流程。

### 把研究要求落实到执行过程

定制工作流也意味着需要持续维护。我希望利用 Agent 的代码工具，协助诊断问题、修改实现和执行测试，让研究方法与具体实现保持一致。

kk-knowledge-base 和 kk-research 就是在这样的实践中逐步形成的。前者规范资料管理和证据获取，后者明确研究模型的上下文边界、取证权限和输入披露方式。每次调整之后，都需要检查实际执行结果。

### KYA：使用者需要理解自己的 AI

在这个过程中，仍然需要我来把握优化方向。负责维护的 Agent 需要了解投研目标、已有设计和修改可能带来的影响；这些信息需要由我提供，并通过具体任务与它反复确认。

因此，我把 KYA（Know Your AI，理解自己的 AI）作为这套实践的重要前提。我需要知道模型看到了什么、工具实际做了什么，以及哪些判断仍缺少验证。通过自然语言生成实现之后，还要检查架构、执行路径和实际结果，才能判断修改是否达到了预期。

这也意味着需要考虑时间投入：哪些环节值得定制，哪些环节交给现成产品，取决于它们能否持续改善研究质量和日常效率。

## 二、选择以 RAG 为主的知识库

### 持续增长的资料，需要能够随问题重新检索

我的研究范围和资料量会不断变化。因此，我选择以 RAG（检索增强生成）作为知识库的主路径：保留原始资料，提问时检索相关内容，再把必要的原文交给模型分析。

对于 LLM-Wiki，我主要顾虑长期维护知识页面的成本。LLM-Wiki 通常会把资料整理成公司、概念或赛道页面，并维护页面之间的引用。页面分类、字段和关联方式共同构成 Schema。随着研究范围扩大、资料增多，使用者需要持续调整这些组织规则。

在我的使用场景里，新的实体、细分赛道、子业务和分析维度会持续出现，已有概念的边界也可能变化。我担心按照某个时间截面和资料规模设计的 Schema，难以长期覆盖后续需求。页面划分偏粗时，正文会越来越长；划分偏细时，页面、链接和索引的维护负担又会增加。

基于这样的增长预期，我更愿意长期保存原文，在每次研究时按问题检索和补读，并让结论能够追溯到具体材料。这是我针对自身场景的工程选择，效果需要通过实际召回、引用能否支撑论断，以及跨资料研究的表现来检验。

### 控制每轮输入，同时保留必要语境

资料越来越多，还会带来模型如何使用长上下文的问题。标称窗口说明模型可以容纳多少输入；复杂任务中的实际表现，还受到模型、材料分布、信息位置和任务要求的影响。Context Rot 指上下文变长后表现退化；Lost in the Middle 指模型对长输入中部信息的利用不足。

因此，我希望控制每轮输入的规模，同时保留理解证据所需的语境。通过 RAG 取得原文后，还需要检查遗漏、补读相邻段落，并保留反向证据和方法限定。在此基础上，kk-research 进一步将研究材料与后台操作记录分开，让我能够核对每一轮分析的实际依据。

这也把两项选择连接起来：用可定制的 Agent 组织研究流程，用原文检索支持资料积累，再通过输入披露和实际验收检查执行过程。下面是这套工作流的具体安排。

## 三、让资料能够保存、找回和阅读

个人知识库通过 AnythingLLM Desktop 解析文件、分块并管理向量存储，使用 Ollama 的嵌入模型在本机建立检索索引。Hermes 负责接收自然语言要求，并调用配套客户端完成入库和检索。

我希望日常使用尽量简单：把资料交给助手，再说明需要做什么。文件整理、去重、来源记录和失败后的继续处理交给后台完成。

不过，文件上传之后，还需要验证能否实际检索到原文。当前规则要求检查解析正文、工作区关联，以及真实向量接口能否召回同一文档的原文。检查通过前，文件继续保留相应的处理中或失败状态。

此外，我也希望自己能直接打开资料阅读。为此，知识库保留按主题整理的阅读文件，使用真实标题命名，并记录准确来源。原始格式需要保留时，继续保存原文件；网页和粘贴正文可以整理成 Markdown。排版调整应保留原文内容。

这样，我既能让 AI 查找资料，也能沿着来源回到材料本身。

## 四、让研究模型有清楚的上下文边界

有了资料库以后，我希望进一步控制研究模型收到的内容。独立研究模式围绕这个目标设计：在可控的请求范围内，只传入用户原始问题、明确要求、必要研究规则、可追溯的材料，以及本项研究的讨论记录。

工具定义、认证信息、操作日志和无关聊天留在执行侧。资料读取失败时，研究模型收到简短的缺口说明；后台保留具体错误与重试记录。

交接材料时，还需要保留证据的适用范围。反向证据、样本范围、统计口径和原作者的限定语都应随原文传入，避免在筛选和压缩时遗漏影响判断的信息。

## 五、四个角色怎样分工

为了把上述要求落实到研究过程，我用四个角色分担接收、取证和分析任务。其中一部分工作由确定性程序完成，分析和讨论交给独立的核心模型。

| 角色 | 职责 |
|---|---|
| Agent 1 | 接收并转交用户问题，默认保留原话 |
| Agent 2 | 检索本地资料，按需要补读原文 |
| Agent 3 | 根据研究模型指出的缺口，从准入的外部来源补充材料 |
| Agent 4 | 判断资料是否充分，提出补证需求，进行分析并与用户讨论 |

在这个分工下，研究判断集中在 Agent 4。负责转交和取证的角色需要准确传递材料，避免先写出结论，再让核心模型顺着结论分析。

研究开始时先查本地资料。Agent 4 阅读后，如果认为仍有缺口，可以提出具体补证要求；资料已经充分时，就停止继续取证。

## 六、让每次研究的输入可以核对

我希望在模型分析之前，能够看到本轮实际检索了什么、取得了哪些资料，以及准备向模型发送哪些内容。

因此，独立研究模式要求在发送前展示材料清单，说明标题、来源、日期、全文或片段范围，以及截断和缺失情况。检索命中、取得正文、装入请求和独立核验分别记录，让我能够区分资料处理到了哪一步。

进一步核对时，还应查看实际发送的请求和传输回执。界面上的角色名称或模式标签只能帮助识别状态；上下文边界需要通过真实请求内容验收。

## 七、证据怎样支撑分析

除了知道模型读到了什么，我还需要判断这些材料能否支撑结论。因此，本地检索保留来源和阅读范围；涉及关键论断时，需要回到原文补读，检查相邻语境、时间和口径。检索匹配度用于排序，事实是否可靠仍要结合正文判断。

外部补证优先使用准入的原始发布，例如公司公告、监管发布、产品官方文档和论文原文。券商研报可以帮助梳理观点、分歧和预测，引用时保留机构与作者归属，并按需要另核关键事实。

取证过程中遇到材料缺失、权限不足或接口失败，就保留具体缺口。研究结论应说明证据能够支持到哪里，以及还有哪些问题需要验证。

## 八、使用边界与公开范围

文件解析、嵌入和存储在本机完成。被选中的检索片段及补读正文会发送给承担分析的模型服务商。使用者需要根据资料敏感程度确认允许发送的范围。

运行这套工作流还需要 Skill 之外的配套实现：kk-knowledge-base 依赖客户端和本地服务，kk-research 依赖 clean-research 插件和会话管理。部署时需要适配公开名称与本机命令的映射，仅下载 SKILL.md 尚不足以复现完整流程。

因此，公开版本需要说明提供了哪些文件、还需要配置哪些依赖，以及实际验证过哪些使用场景。换用电脑、服务版本或金融接口后，也需要重新检查相应功能。

## 我希望保留的原则

- 资料可以方便地投递，也可以由人直接阅读。
- 入库结果通过真实检索验证，失败和处理中状态清楚保留。
- 研究模型接收的内容有明确边界，用户能够核对实际输入。
- 接收问题、取得材料和形成判断各有职责。
- 引用能够回到原文，结论保留证据的适用范围。
- 缺少材料时说明缺口，后续围绕缺口继续验证。

kk-knowledge-base 和 kk-research 记录了我对 AI 辅助研究的具体要求。随着实际使用，我会继续调整它们，并根据执行结果检验这些设计。
